# Pipeline and feasibility probe architecture

The offline comparison pipeline below is Milestone 1. A separate optional Milestone 2 feasibility probe is described at the end; the integrated Milestone 3 runner is described below.

`tasks.py` loads the versioned development task contract, validates probabilities and positive evidence denominators, enumerates scenario/condition/label cases, calculates exact-fraction targets, and renders self-contained requests. `pipeline.py` gives both scripted deployments identical model-visible inputs, records their supplied outputs and stop statuses, and saves `raw.json`. `scoring.py` reads saved records, verifies the complete planned set and identities, parses probabilities, computes independent losses, and aggregates within scenarios. `report.py` combines saved raw records and scores into escaped static Markdown. `cli.py` exposes `fixture`, `score`, and `report` commands.

## Records and ownership

All JSON has explicit schema versions. Nested scenarios and conditions inherit `cib.fixture.v1` and the task/dataset versions; their IDs are scoped by those versions. Their contract includes provenance, split, construct, grouping, protocol, inputs, and development analysis policy. Likelihoods and priors are model-visible facts. Annotations and derived posterior targets are scorer-only metadata. `request.input` is the **entire provider-visible payload**, containing messages alone; its serialized shape is tested against an allowlist. The raw artifact and manifest are audit records and must never be supplied wholesale to a real model.

- `cib.run.v1`: a raw artifact containing dataset, manifest, requests, and attempts. It is written with exclusive creation and never edited by scoring/reporting.
- `cib.manifest.v1`: run UUID, UTC timestamp, source fingerprint, Git revision/tree state (unknown revision when unavailable), Python/hardware, dataset hash, full scripted provider configuration, deployment registry, and explicit analysis choices. Seeds, decoding/output limits, and retry policy are recorded on requests; inapplicable settings are labeled. No weights/tokenizer/hardware inference precision exists for the scripted provider.
- `cib.deployment.v1`: deployment ID, synthetic kind, provider version/script hash, and explicit inapplicable model properties. IDs cannot masquerade as real reference/compressed deployments.
- `cib.request.v1`: deployment ID, scenario/cluster, task version, condition, label variant, prompt variant, trial, stage, exact model-visible input, input hash, and decoding. Request IDs hash deployment, complete pairing key, actual input, and decoding. Pairing keys omit deployment, but both sides must have distinct declared deployment IDs, identical key sets, identical inputs, and identical decoding.
- `cib.attempt.v1`: request/deployment ID, attempt index, timestamp, exact raw output (null when no output), supplied status, stop reason, and error. The fixture has exactly one attempt per request, including scripted infrastructure failures. No failure is removed from the planned set.
- `cib.scores.v1`: raw file hash, run/dataset identity, scorer version/source fingerprint, analysis configuration, per-request `cib.score.v1` parse/status records, per-condition `cib.condition-score.v1` diagnostics and independent targets, per-scenario coverage/metrics/bounds, and a paired comparison. Each condition score retains its pre/post request IDs. Parser behavior is versioned together with the scorer.

Raw validation rejects changes to supported fixture definitions, mismatched deployment identities, missing/duplicate planned requests or attempts, altered inputs, and inconsistent attempt ownership. This implementation supports the pinned v1 fixture; changing the instrument requires a new supported version. It is not a general experiment configuration runner yet.

## Derived artifacts and missingness

Rescoring creates a new scores file with source and raw lineage. Report generation verifies that saved scores belong to the exact raw file/run/dataset/configuration and displays both artifact hashes. All commands refuse to replace existing destinations. Files can still be manually edited outside this tool; hashes provide lineage checks, not tamper-proof storage.

Missing probabilities remain null. Prior/posterior losses can be scored independently; update and drift diagnostics require both stages. Drift is eligible only for uninformative conditions. Each metric's scenario mean requires all eligible conditions/variants. A posterior contrast is shown for complete paired scenarios; the full planned-set contrast is withheld unless all scenarios are complete. Conservative full-set contrast bounds preserve observed losses and use [0,1] for missing posterior losses, without renormalization. No bootstrap or other inferential uncertainty is implemented.

The static report exhaustively includes all fixture pairs and failures. Raw content is escaped inside text blocks. New response production varies timestamps/UUIDs; rescoring the same saved raw bytes with the same scorer produces identical score bytes. Regeneration never invokes the response producer. Default unittest checks run offline using independent analytic examples and temporary artifact directories.

## Milestone 2: explicit local MLX feasibility probe

`python -m cib.feasibility` is separate from the fixture CLI and does not change its deployment registry or raw schemas. MLX/Hugging Face dependencies import only inside explicit preparation/check execution; default offline tests import no inference libraries. `configs/feasibility-qwen25-1.5b.json` pins source revision, precision, backend versions, direct weight-quantization settings, request selection, generation controls, and local budget. Unsupported controls are rejected rather than silently ignored.

`prepare` downloads the official source snapshot, checks its unquantized BF16 tensors and official LFS hashes, saves the original source inventory, and converts a local 4-bit derivative without calibration data. `cib.prepared.v1` records both file inventories, configuration hash, dtype counts, dependency/source fingerprints, conversion time, and memory counters. Binary artifacts and caches stay in Git-ignored locations. Conversion emits reserialized tokenizer files, but generation deliberately uses the original source tokenizer for both deployments.

`check` validates preparation/config identity and both relevant file inventories before loading one deployment in a fresh process. It sets offline Hub/Transformers mode, records loaded tensor/module precision, original EOS IDs, and original template. Only renderer-produced messages enter chat templating; annotations/targets/configuration never enter the model. Each `cib.feasibility-attempt.v1` retains task/stage identity, exact messages, rendered input, token IDs, raw text, stop status, format diagnostic, wall time, memory, and cache dtype. Per-request records are written before inference and streamed text/token events flush to JSONL. There are no retries, output caches, or probability-error scores. The development parser is reused solely to diagnose strict formatting; malformed responses remain null probabilities.

The command creates a new output directory, saves an invocation/configuration snapshot before inference, and retains errors separately. Existing directories and files are not overwritten. An error in a completed check is retained and makes the command fail; no automatic retry occurs. A hard process failure can leave invocation/request/stream records without a final check artifact. These files must not be treated as successful generations.

Small real smoke outputs, source identities, hardware, and failure records are versioned under `docs/evidence/m2/` and audited offline. They carry feasibility labels and are not fed to the synthetic fixture scorer/report CLI. Native MLX allocator peaks and macOS process peak RSS are separate byte counters. Timing begins after artifact hashing, so file caches can be warm. Full resume, retries, stop/refusal mapping for study use, paired scoring, and report integration remain Milestone 3 responsibilities.

## Milestone 3: real adapter integrated with saved-output scoring

`runner.py` plans the full pinned development task set with `pipeline.planned_requests`, replaces scripted decoding/deployment identities with real fingerprints, and owns `cib.real-run.v1` / `cib.real-manifest.v1` snapshots. Each manifest embeds the configuration, prepared artifact inventories, dataset, analysis, retry limit, code fingerprint, and complete observation plan. `mlx_adapter.py` imports optional MLX libraries only when a pending real attempt needs them. It verifies local files, loads one artifact with the original source tokenizer, audits loaded precisions, renders messages to exact text/token IDs, and streams generation events. It never receives the task dataset, answer targets, or scorer annotations. The existing feasibility probe remains independently usable.

Data flow: task messages → adapter rendering → immutable attempt start → flushed token/text stream → immutable result → full-plan raw snapshot → `cib score` (explicit parser) → `cib report`. Scoring/reporting share the existing analytic targets, pairing, scenario aggregation and missing-loss policy with fixtures. Raw schema dispatch keeps fixture validation strict and adds real-record validation without assigning real responses synthetic deployment identities. Pairing checks both messages/decoding and actual rendered text/token IDs when both sides exist. The final allowed attempt supplies each observation's score; all attempts remain in raw records/reports and attempt coverage counts.

A run directory holds `run.json`, `.lock`, deployment loaded metadata, and `<request-id>-<attempt-index>.start.json`, `.stream.jsonl`, `.result.json`. Setup failures get separate uniquely named records. JSON files commit through a temporary file and exclusive hard link after flushing/fsync, so an interrupted commit cannot leave a truncated canonical result. The process lock serializes generation and CLI export. Temporary commit remnants after an OS kill are never treated as observations. Snapshot export also represents unfinished attempts as interrupted infrastructure errors without modifying journals; resume commits that recovery result before considering the single allowed infrastructure retry. This provides process-interruption recovery, not a guarantee against disk loss or power failure. Streams flush per event; they are not fsynced per token.

Requests add a deployment fingerprint to their content identity. Cache identities also cover actual text/token IDs, decoding and the full task/trial key. The journal is the only cache and has no cross-run output reuse. Resume validates the original plan and rejects changed config/preparation. A terminal attempt is skipped, even when its output is malformed, incorrect or truncated. An infrastructure failure may be retried once on a later invocation. Pending observations are budgeted by `--limit`; a repeated positive limit advances the run rather than replaying its completed prefix. `--limit 0` provides a no-generation check. The bounded real check retains the full planned set as missing rather than manufacturing complete scenario coverage.

`import-m2` checks preparation/config/source lineage, backend, original selection identities, message hashes, template/EOS agreement, and rendered/tokenized pairing. It creates a derived real raw artifact with complete original attempts and source paths/hashes; it does not edit M2 files or invent absent pre responses. `not_attempted` placeholders are not counted as inference attempts. Strict and diagnostic score files are separate; each real score file also displays both format coverage counts. The report shows all planned pairs, all attempt histories, per-observation probabilities, independent condition losses, scenario coverage and bounds, and artifact lineage. Raw content remains escaped text.

Versions: `strict-probability-v1` remains primary; opt-in `outer-json-fence-v1` uses `updating-diagnostic-v1`. Strict scoring retains `updating-scorer-v1` with source fingerprints; extended real coverage fields do not change its numerical definitions. All outputs use exclusive destinations. See D006–D007 for parsing, retry, refusal and incomplete-data decisions. Only the pinned development instrument and this MLX deployment pair are supported; no generic backend registry or empirical uncertainty estimator is introduced.

## Milestone 4: pinned exploratory pilot

`tasks.load_pilot()` owns a separate versioned dataset, with its complete protocol also in `configs/pilot-v1.json`. The fixture remains pinned and unchanged. `pipeline.planned_requests` reuses the self-contained renderer with three pilot templates; `pilot.extend_plan` adds sixteen message-only controls and twelve trial-1 repeats per deployment. Scorer targets stay in the dataset, outside adapter payloads. The runner's explicit `--pilot` initializes 344 requests and embeds the protocol before generation; resume validates the complete dataset/plan and prepared configuration. Each observation has at most two infrastructure attempts, bounding total calls at 688. Between-request wall/memory/disk ceilings can stop work with explicit unexecuted observations; they do not interrupt an in-flight call. Generation time and native MLX/process memory counters are saved on new attempts. Earlier files are not amended.

`python -m cib.pilot score` validates saved real records and reuses the unchanged `outer-json-fence-v1` parser and analytic scorer, with `updating-pilot-scorer-v1` primary-policy metadata and an implementation hash. Main condition/scenario metrics use trial 0 only. Controls, repeat consistency, template/condition diagnostics, complement sensitivity, baselines, coverage and costs are separate fields. Full-set means remain missing when any required scenario is incomplete; existing complete-scenario contrasts and posterior missing-loss bounds remain exposed. Strict compliance uses all eligible EOS completions, including malformed text, while primary coverage exposes the full planned denominator and completed counts. Generic fixture/M3 scoring retains historical defaults/labels. The generic report rejects pilot data to avoid mislabeling the primary policy; use `python -m cib.pilot report`.

`pilot_report.py` renders a readable summary and exhaustive exact requests, attempt texts/statuses, controls and condition losses from saved artifacts, checking raw/run/dataset lineage and escaping output. `scripts/verify_pilot.py` creates a new offline audit directory, hashes the original run files, regenerates scores/reports twice, checks byte identity within that source version and numerical equality with original scores, and confirms original files unchanged. Report-only source changes are preserved as source lineage. Compact real evidence is in `docs/evidence/m4/`; bulk raw snapshots, loaded metadata and immutable token streams remain under ignored `outputs/`. No backend/service abstraction or empirical confidence estimator was added.

## Milestone 4b: evidence audit and fixed wording diagnostic

`scripts/audit_m4b.py` reads immutable M4 records, checks paired messages/decoding/rendered tokens, reconstructs likelihood targets and main Bayes targets/losses from exact visible prompts, and records control/drift/prior discrepancies with original hashes. It never generates responses or overwrites source records.

`diagnostic.py` owns a separate pinned dataset/protocol and three equivalent representations, request identities, main scenario aggregation, control/repeat diagnostics and predeclared competence screens. `pipeline.planned_requests` dispatches that schema to its planner; the existing runner validates the entire pinned dataset, preserving original fixture/pilot request order and identities. Diagnostic observations have at most one infrastructure retry and a hard total-attempt ceiling, including repeats, enforced before each new attempt. Unexecuted work remains distinct from failures. The pair plans180 calls under 200 maximum; the explicitly scoped single-reference plan has60 under 100 maximum. No backend registry was introduced.

`larger_reference.py` implements only the separately authorized Qwen2.5-7B BF16 preparation: pinned public revision, official hashes/sizes, saved unquantized tensor headers, source tokenizer and no conversion/quantization. The same MLX adapter checks actual loaded BF16 tensor count and absence of quantized modules. Its registry contains only `reference`; it never creates a paired quantized condition. The56 common trial-0 prompts are identical to the clearer wording subset, with four separate repeats.

`diagnostic_report.py` renders saved scores/inputs/all attempt histories with escaped raw text and lineage checks. `scripts/verify_diagnostic.py` checks historical/new immutable-file inventories, numerical equality across source versions, repeated score/report byte identity, streamed text and BF16 KV without inference. Bulk journals, weights and raw snapshots stay ignored; compact audited/measured evidence is versioned under `docs/evidence/m4b/`. Historical policies/scores are unchanged. The diagnostic narrows a competence issue, rather than extending the frozen benchmark or selecting a final reference.
