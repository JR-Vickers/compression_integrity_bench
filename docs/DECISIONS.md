# Decisions

## D001 — Offline implementation and artifact format

Status: accepted for Milestone 1, 2026-11-12. No superseded choice.

Use Python >=3.11, standard-library runtime/tests, JSON artifacts, and a Markdown report. Setuptools >=68 supplies packaging and the CLI entry point; source execution needs no build dependency. This keeps verification independent of networks, credentials, downloads, and accelerators. A single raw JSON artifact owns the planned request set, all one-attempt records, task snapshot, and manifest. Scoring and reporting are separate commands that create new files exclusively. Consequence: the fixture runner is intentionally small and has no production resume or retry functionality. These remain Milestone 3 work.

## D002 — Explicit development instrument and missing-data policy

Status: accepted only for development fixtures, 2026-11-12. No superseded choice.

Adopt the proposed self-contained pre/post numerical updating task to exercise the offline pipeline. Hand-author two base scenarios with three branches and two label variants. Each branch/variant has its own pre request; those repeated priors are engineering checks, not independent scenario samples. Both scenarios share a template cluster. Perfect response scripts use hand-entered probabilities; the scorer computes targets separately with exact fractions before float loss calculations. Computational rounding is not a behavioral acceptance threshold.

Use strict JSON probability parsing and distinguish malformed, refusal, truncation, infrastructure error, and valid numerical responses. Providers script stop-status metadata; a real adapter must later define its own mapping. Script the same planned set for both providers; never reprompt malformed answers. Average equal-weight conditions/label variants within scenario, then equal-weight scenarios. Each scenario metric requires complete eligible conditions; report coverage, complete-scenario posterior contrasts, and full-set conservative missing-loss bounds. Bounds use the global [0,1] posterior-loss range and can be wider than target-specific attainable bounds.

Consequences: these fixtures validate plumbing and scorer behavior only. They do not select a checkpoint, backend, study population, sample size, final endpoint weights, parser policy, or preservation margin. Direction and stability tolerances remain null. No empirical calibration, compression, or preservation claim is supported. Held-out study choices remain unresolved in METHODOLOGY.md.

## D004 — Local pilot deployment pair

Status: accepted for Milestone 2 feasibility only, 2026-11-12. No superseded model selection. This does not select the final study population or remove the proposed MoE work package.

Select the official instruction-tuned [Qwen/Qwen2.5-1.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct), revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`, with its original **BF16** weights as the unquantized reference. Locally derive one **4-bit affine, group-size 64** weight-quantized artifact using MLX-LM **0.32.2**, MLX/MLX-Metal **0.32.4**. No calibration data or quantizer fitting is used. The official source is public/ungated and Apache-2.0; its downloaded LICENSE is retained with the source snapshot. Source weight SHA-256 was checked against the official Hub LFS metadata. The locally derived artifact is identified by file hashes, not a third-party model name.

The actual machine is macOS 15.7.7 on an M4 Max MacBook Pro, 16 CPU cores (12 performance/4 efficiency), 40 GPU cores, 64 GiB unified memory. Initial disk headroom was 239 GiB; `vm_stat` showed about 13.75 GiB immediately free plus about 3.60 GiB purgeable, no swap I/O, and `memory_pressure` reported 91% system-wide memory free. These are different OS counters, not interchangeable estimates of available memory. Post-download disk headroom was 234 GiB. Existing tools included llama.cpp 0.7.0 build 11669 (`620d2225c`), Ollama, hf 2.2.0, and uv 0.13.5. MLX-LM was installed in an isolated, Git-ignored Python 3.11.17 environment. Budget: local hardware and free artifacts only, no paid compute; six generations per deployment, plus an identical repeat solely to repair metadata inspection.

Alternatives were checked against official publisher model cards/APIs and the [MLX-LM qwen2](https://github.com/ml-explore/mlx-lm/blob/v0.32.2/mlx_lm/models/qwen2.py) and [qwen3](https://github.com/ml-explore/mlx-lm/blob/v0.32.2/mlx_lm/models/qwen3.py) implementations:

| --- | --- | --- | --- |
| `Qwen/Qwen2.5-1.5B-Instruct` | `989aa7980e4cf806f80c7fef2b1adb7bc71aa306` | Public, ungated, Apache-2.0; qwen2 supported | Selected; small download and comfortable memory margin with a simple non-thinking protocol |
| [Qwen/Qwen2.5-0.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct) | `7ae557604adf67be50417f59c2c2f167def9a775` | Public, ungated, Apache-2.0; qwen2 supported | Smaller fallback; not downloaded or run because memory did not require it |

Availability, provenance, and source-code support were verified for alternatives; runtime compatibility was observed only for the selected pair. No candidate was chosen or rejected on benchmark scores. The larger names in the original proposal remain provisional, with no availability claim made here. MLX was selected over installed llama.cpp/Ollama because it loads the official safetensors directly and [converts them locally](https://github.com/ml-explore/mlx-lm/blob/v0.32.2/mlx_lm/convert.py), preserving a straightforward derivation chain without a third-party GGUF conversion. No cross-backend experiment is needed for this feasibility check.

Controls: both deployments run on the same Metal device, in separate sequential processes, using the **same original source tokenizer**, original chat template and its default system message, exact messages, rendered inputs, and input token IDs. The converter reserializes tokenizer files; those derivative tokenizer files are deliberately not used. EOS IDs `[151643, 151645]` come from the pinned source generation configuration. Greedy temperature 0, seed 0, 64 new tokens, 2048-token input-plus-output acceptance limit, prefill step 512, no extra stop strings, penalties, constrained decoding, conversation history, or retries. The native configured maximum context is 32768; this check does not exercise it. There is no separate reasoning mode in this checkpoint. KV quantization is disabled; actual KV tensors were BF16 in every check.

Quantization covers all 197 eligible modules: 28 layers × seven projection matrices plus the tied embedding/output matrix. Norms, ordinary projection biases, and affine quantization scales/biases remain BF16. The saved reference has 338 BF16 tensors; the derivative has 197 packed uint32 tensors and 535 BF16 tensors. Nominal four bits describes quantized matrix elements, not total artifact bits/parameter; conversion reports about 4.501 effective bits/weight. Artifact sizes are 3,087,467,144 and 868,629,082 weight bytes respectively. Tensor/module inventories, hashes, and complete controls are saved in [evidence](evidence/m2/README.md) and `configs/feasibility-qwen25-1.5b.json`.

Confounds and limits: dense BF16 and affine-quantized matmul/embedding kernels differ. Floating-point accumulations and intermediate casts use the pinned backend's implementation; an all-BF16 arithmetic graph is not asserted. Source weights and actual KV precision are verified. Loading order was reference then quantized; hashing pre-read files and warmed the OS cache. Timings include startup effects and normal machine activity and are not throughput benchmarks. No precision isolation beyond this declared deployment intervention is claimed.

Observed: each deployment loaded and completed all six prompts at EOS without truncation after the metadata fix. **All twelve outputs are Markdown-fenced JSON and fail the unchanged strict bare-JSON parser.** Parsed probabilities remain null; no posterior loss, compression effect, or preservation result is reported. Loading/generation feasibility is established; strict-format reliability is not established and must be addressed explicitly during instrument development before a scoreable pilot. This failure is retained, not used to switch models or silently relax parsing.

## D006 — Separately versioned outer-fence diagnostic

Status: accepted for exploratory Milestone 3 diagnostics, 2026-11-12. Supersedes no primary parser or earlier result.

Keep `strict-probability-v1` and default bare-JSON scoring unchanged. Add opt-in `outer-json-fence-v1` (`updating-diagnostic-v1` scorer): accept bare strict JSON or exactly one outer triple-backtick fence, with an empty label or lowercase `json`, newline after the opener and before the closer, and optional surrounding whitespace. Strip only this wrapper, then call the same strict schema/probability validator. Reject prose, multiple/nested fences or objects, duplicate keys, strings/booleans, nonfinite/out-of-range values, and extra fields. No coercion, answer extraction, reprompt, or probability inference from prose.

This is a methodology amendment made after inspecting development responses, explicitly exploratory and applied symmetrically. Both score artifacts retain their parser/scorer/source versions and raw hashes. Reports display primary strict compliance and diagnostic scoreability together, with separate numerical analyses. M2's original null parsed probabilities and raw evidence remain unchanged. Final study parsing is still unresolved; this change does not repair format compliance or validate the instrument.

Audit established that all 12 M2 fences originate in generated token IDs. Every concatenated stream and independently decoded generated token sequence equals its saved raw response; no rendered input contains a fence. Initial emitted tokens include `73594` (triple backticks), `2236` (`json`), and `198` (newline). MLX-LM's installed `stream_generate` yields detokenizer segments and marks EOS as `stop`, budget exhaustion as `length`; the probe concatenates those segments without wrapping them. The original template supplies `You are Qwen, created by Alibaba Cloud. You are a helpful assistant.` and the assistant generation prefix. There is no answer in that prefix. Detailed controls, precision findings, hashes, and limitations are in [M3 evidence](evidence/m3/README.md).

## D007 — Narrow local MLX runner, recovery, and incomplete-set reporting

Status: accepted engineering policy for Milestone 3, 2026-11-12. Extends D001/D002/D004; supersedes the probe's zero infrastructure retries **only for the new runner**. M2 artifacts and probe behavior are unchanged.

Reuse the pinned artifact/decoding configuration and prepared inventories. Plan the full existing development instrument: 24 requests per deployment, trial 0, 48 observations total. M2's six selections govern only checked legacy import, never redefine the full scoring denominator. The bounded integration check executes the first six requests per deployment in the deterministic task order; M2 import selects its original six, which include the rare-prior case. These are separate datasets of engineering observations and are never pooled. The manifest records the complete plan and policy. No final model, task sample, inference budget for a study, or threshold is selected.

Use one optional MLX adapter, one deployment per sequential process, exact original tokenizer/template, original EOS IDs, no constrained decoding, and the same BF16 KV policy. Verify model files and actual loaded tensor precisions. Model-visible payloads contain messages alone. Record actual rendered text/token IDs before generation and each streamed event before parsing. EOF with no terminal reason is an infrastructure error, `length` is truncation, and EOS `stop` is completion. MLX supplies no refusal flag: textual refusals are malformed under these numerical parsers; refusal recognition is not inferred heuristically. Explicit refusal statuses remain supported by scoring.

The runner permits at most one retry after an infrastructure failure, including interruption. A subsequent invocation retries that observation once; no within-invocation retry loop. All other returned outcomes are terminal, including malformed or incorrect answers and truncations. This runner retry limit is separate from the retained M2 probe configuration's `generation.retries=0` (the adapter makes one generation call per attempt). Every attempt remains saved. Setup failures are saved separately and are not invented model observations. A process lock prevents concurrent writers. Exclusive atomic JSON commits prevent torn result files. An interrupted stream remains immutable; its complete events supply partial text and the final torn event, if any, stays in the stream. Unexecuted observations remain `not_attempted`, distinct from infrastructure failures.

Request identity includes deployment fingerprint, task/trial identity, messages, and decoding. The additional cache identity includes actual rendered text/token IDs. Model and tokenizer inventories, revision, quantizer and backend versions enter deployment fingerprints. The journal is the only response cache; there is no cross-run reuse. Completed observations are skipped without loading MLX. Resume rejects changed configuration/preparation/planned inputs. Reusing a run directory with a positive budget continues with pending observations; `--limit 0` executes none. Export creates an immutable full-set raw snapshot; scoring/reporting never load a model. Imported M2 records retain source hashes and complete original attempts and loaded metadata.

Apply the existing equal-condition, equal-scenario, complete-scenario policy and [0,1] missing-loss bounds. Do not broadcast one pre answer into several branches or average the six observed outputs as if they were a complete instrument. Both M3 reports withhold scenario contrasts; diagnostic per-response losses are legitimate descriptive values against independent analytic targets. No inferential intervals or preservation conclusions are supported.

Controls and repeats are separate diagnostics; matched numerical patterns across templates constrain generalization. No threshold or final model is selected by this pilot. Findings and limitations will be appended after the complete allocation, without changing this protocol.

### D008 observed outcome and consequences

The complete fixed allocation produced 344/344 EOS and primary-scoreable responses with no inference retries; strict compliance remains 0/172 per deployment. All twelve repeated texts/statuses per deployment match. Main numerical coverage is 144/144 each (72/72 prior/posterior/update terms, 24/24 drift), 12/12 complete scenarios. BF16/4-bit posterior losses 0.17446055/0.18287535 both exceed unchanged-prior baseline 0.13601504 (72/72 hypothetical targets). Both score 0/4 likelihood controls despite 4/4 other control kinds, all primary-scoreable. Thus wrapper acceptance enables diagnosis but does not establish instrument validity or reference competence. Context-specific quantized prior complements and irrelevant drift reinforce that limit. Both individual improvements and regressions are retained in [M4 evidence](evidence/m4/README.md).

Retain this negative competence finding without changing the pilot or silently selecting a new model. Next dependency: a fresh exploratory instrument/reference-suitability check targeting the control failures before a frozen updating protocol, alongside Milestone 5's broader module preparation. No primary-policy revision for historical results, held-out model selection or preservation threshold is made. Saved raw records remain immutable; report-only source additions have new source lineage and unchanged numerical results. Local workflow completion satisfies M4's assessment criteria, not final-study validity.
